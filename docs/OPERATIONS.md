# Nolya 生产运维准备与恢复手册

本目录提供部署准备，不表示已经上线、完成云资源配置或通过生产容量/安全审计。所有示例中的域名、路径、备份周期和告警接收人必须由运营方确认。不要对真实服务运行写入型测试。

## 发布门槛

- 使用固定 Git 提交及锁文件；运行 `./scripts/verify.sh`、`python3 scripts/ops/test_backup.py`、`python3 scripts/ops/test_api_restore.py`。后者启动隔离端口和临时数据库，不接触现有服务。
- 在独立预发布环境构建并运行 Docker 镜像，记录基础镜像解析出的 digest；发布前扫描镜像及依赖。CI 提供构建检查，但不自动发布、推送镜像、申请证书或部署。
- 确认 HTTPS 域名、域名所有权、TLS、隐私政策、服务条款、账户恢复/客服流程、限流及滥用处置、监控和备份恢复负责人。本产品提供预先生成的一次性恢复码，不提供邮箱、短信或微信登录/找回。密码与恢复码都丢失时没有绕过账户验证的客服恢复渠道。
- 对目标并发和数据量执行容量测试。SQLite 仅支持单实例本地持久磁盘；不要横向扩容多个应用副本、把 DB 放 NFS/共享网络文件系统或把容器可写层当持久存储。
- 恢复演练必须实际从外部备份取回文件并启动对应应用版本。仅检查备份存在不是恢复能力证明。

## 配置及进程

`deploy/nolya.env.example` 是 systemd 配置样例；`deploy/compose.yaml` 是容器样例。生产必须设置：

- `NOLYA_ENV=production`，`NOLYA_PUBLIC_ORIGIN=https://你的域名`。
- `NOLYA_COOKIE_SECURE=true`，`NOLYA_ALLOWED_ORIGINS` 仅精确 HTTPS Origin，不带路径、通配符或开发端口。
- DB 与静态目录使用明确绝对路径；进程非 root，数据目录 0700，配置文件 0600。
- `RUST_LOG=nolya_api=info,tower_http=warn`；不要记录 Cookie、Authorization、密码、邀请 token、请求体、完整 URL 或导出内容。
- 后端只对反向代理开放。systemd 监听 localhost；Compose 不发布 app 的 3000 端口。

应用暴露 `/api/v1/health/live`（进程存活）和 `/api/v1/health/ready`（数据库可读）；原 `/api/v1/health` 保留兼容。Caddy 阻止公网 health 路径，容器及本机监控直连后端。就绪探针不是磁盘可写性、备份新鲜度或完整业务链路保证。监控应另行检查磁盘空间、写失败、备份年龄、业务错误率与延迟。建议磁盘剩余低于 20% 预警，低于 10% 紧急处理，具体阈值经容量验证后设定。

### 容器示例（操作前需独立授权）

在 `deploy` 目录设置 `NOLYA_DOMAIN`（实际域名），然后检查 `docker compose config`。有实际部署授权后才能执行 `docker compose up -d --build`。Caddy 会向证书服务申请证书，要求 DNS 和 80/443 可达；这不是无副作用的配置检查。

默认采用命名卷 `nolya_data`，镜像内该目录属 UID/GID 10001、权限 0700。首次启动后验证卷内所有权及权限；若换绑宿主目录，提前由管理员创建同样权限，不能 `chmod 777`。严禁 `docker compose down -v`，它会删除持久卷。

容器镜像不包含 Python 备份工具。备份由宿主机或单独受控维护环境运行，通过只读源卷访问 SQLite；备份进程仍须具备读取 DB/WAL/SHM 的权限。在 Linux Docker 主机确认实际卷路径后，按下面命令使用，不猜卷名或挂载点。SQLite 源数据库开启 WAL 时，读取需能访问 WAL/SHM；不要使用 immutable 模式绕过日志。

### systemd 示例

由管理员创建 `nolya` 系统用户，安装不可由服务用户写入的版本目录 `/opt/nolya/releases/<版本>`，并将 `/opt/nolya/current` 链接到目标版本。安装环境文件、单元文件及反代配置后再启用服务。systemd 自动创建 `/var/lib/nolya`。`deploy/Caddyfile` 的上游 `app:3000` 仅用于 Compose；systemd 模式必须改成 `127.0.0.1:3000`。

进程接收 SIGTERM/SIGINT 后优雅结束；外部进程管理器等待 30 秒后才强杀。一次只运行一个应用实例。

## 请求限制及滥用控制

应用请求体限制 32 KiB；Caddy 示例也限制 32KB，并配置请求头 10 秒、请求体 15 秒、响应写入 30 秒、空闲连接 2 分钟，以及上游连接 5 秒/响应头 30 秒。上线前必须用实际代理版本验证配置并测试慢请求、超限请求和错误响应。

应用内认证全局 30 次/分钟、游客创建全局 120 次/分钟是单实例安全上限，不是 IP 级反滥用方案，也不是横向扩容容量保证。公网入口需要独立 WAF/网关的 IP/行为限流与告警；标准 Caddy 镜像没有在此配置中启用限流模块。不要直接信任客户端传入的 X-Forwarded-For；如加入 CDN，按已验证代理来源配置 trusted proxies 后再使用来源 IP。阈值需根据真实负载调优，避免共享出口用户被误伤。

## 一致备份

需要 Python 3.11+。使用 SQLite Online Backup API，包含已提交 WAL 内容；不直接复制正在运行的 `.sqlite` 文件。备份经过 integrity_check 和 foreign_key_check 后以原子、拒绝覆盖方式发布，并生成 SHA-256 清单。输出只含生成文件名或状态，不输出记录。目录必须 0700，文件 0600。检查执行退出码；备份未完整写入清单时不能用于恢复。

```sh
# 以能读源 DB 的服务账号执行；使用实际私有路径。
python3 scripts/ops/sqlite_backup.py backup \
  --source /var/lib/nolya/nolya.sqlite --directory /var/lib/nolya/backups
python3 scripts/ops/sqlite_backup.py verify \
  --source /var/lib/nolya/backups/nolya-<实际文件名>.sqlite
```

备份包含用户敏感数据及有效会话材料，权限保护不等于加密。备份必须放在加密磁盘/加密对象存储中，上传须遵循数据授权与访问控制；当前脚本不会上传或创建凭据。SHA-256 仅检查意外损坏，不防止攻击者同时篡改数据库和清单。异地保留应使用独立受限账户及对象版本/不可变策略，由运营方配置。

建议初始目标：每小时备份（RPO ≤ 1 小时）、每日异地拷贝、每月恢复演练，RTO 目标 1 小时。它们是待演练验证的目标，不是已经启用或保证的 SLA。此提交不安装任何定时任务。

## 恢复、升级与回滚

1. 暂停新流量、停止应用。保留当前 DB、WAL、SHM 和应用版本，确认停机窗口及可能丢失备份之后的新增数据。
2. 使用 verify 校验选定备份；记录对应应用提交和迁移版本。备份清单不自动记录应用版本，发布记录必须额外保存该映射。
3. 恢复到新的空路径（脚本拒绝覆盖任何现存 DB、WAL、SHM、journal）：

```sh
python3 scripts/ops/sqlite_backup.py restore \
  --source /var/lib/nolya/backups/nolya-<实际文件名>.sqlite \
  --destination /var/lib/nolya/restore-<事件编号>/nolya.sqlite
```

4. 先在不对公网开放的隔离进程使用恢复副本启动匹配应用版本，验证就绪、数据完整性及人工抽查。不在真实用户库运行测试注册、清理或 E2E。
5. 应用保持停止，人工更新 `NOLYA_DB_PATH` 指向验证后的新文件，保证服务用户有访问父目录及写 DB/WAL/SHM 的权限；启动对应版本并验证健康和关键路径后恢复流量。原数据库保留，禁止把新 DB 覆盖到遗留 WAL 旁。
6. 记录恢复时间、恢复点、丢失数据窗口、校验结果、操作人；必要时按隐私/事件响应制度通知受影响用户。

升级前执行在线备份并校验，记录镜像 digest、Git 提交、配置（不含秘密）及迁移号。应用启动会自动迁移，因此数据库迁移不能假定可逆。回滚前先判断旧二进制是否兼容新 schema；不兼容或不确定时，停止服务、恢复升级前备份到新路径并使用对应旧版本。回滚到旧备份会丢失升级后写入，必须取得该损失窗口的确认。不要尝试手动删除迁移记录或“降级” SQL。

## 保留策略和维护

```sh
# 默认 dry-run，仅列出超过 30 天的候选快照，不改 DB。
python3 scripts/ops/sqlite_backup.py retention --directory /var/lib/nolya/backups --days 30
# 已核对清单并取得删除授权后才加 --apply。
```

保留至少最新一份快照，仅删除完整且校验通过的备份对；损坏/不完整文件会使维护停止而非盲删。离线副本、法律保留、用户删除要求和备份到期处理须单独定义。不要自动删除账户、答题、日记或互动记录；本工具不对业务 DB 做保留清理。备份保留脚本不应与备份、恢复并发执行；操作目录必须由受信任服务账号独占写入。

## 故障处置

- 磁盘满：暂停写流量，扩容或按已批准保留策略清理已验证外部备份；不要删除活跃 WAL、SHM 或业务 DB。
- DB 损坏：停止服务，保全现场，只在复制品上调查，按已演练备份恢复。禁止将 `PRAGMA integrity_check` 输出的用户内容贴进公开工单。
- 就绪失败：检查进程、挂载、所有权、磁盘和迁移错误；不通过重建 DB“修复”。
- 会话或邀请泄露：隔离入口、保存最少必要证据、按事件响应流程撤销相关会话/邀请并通知负责人。不要把日志或 DB 附件直接发送给第三方。
- 演练后：清除隔离环境中的合成数据/授权副本，保留不含个人信息的测试结果。

## 当前验证与边界

已在隔离临时目录验证：运行中 WAL 数据一致备份、checksum/完整性检查、恢复后重新打开及写入、现有文件拒绝覆盖、路径/权限保护、损坏检测、保留 dry-run、保留最新快照。真实编译 API 的隔离数据库备份后恢复并重启通过健康检查及合成 sentinel 持久化检查。

当前执行环境没有 Docker，所以 Dockerfile、Compose、Caddy 的实际构建、TLS 证书申请、卷权限和容器生命周期尚未运行验证；CI 配置尚未在托管 runner 上执行。systemd 样例尚未安装启动；本机静态验证也因 /run/systemd 为只读而不能完成。正式发布必须补齐这些验证，不能把配置文件存在当作已部署证据。
